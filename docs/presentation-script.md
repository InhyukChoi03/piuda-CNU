# 피우다 2.0 8분 발표 시나리오

이 문서는 현재 저장소의 실제 구현을 기준으로 한 기능·기술 중심 발표 대본이다. 전체 시간은 **정확히 8분(480초)**이다. `발표 멘트`의 인용문만 실제로 말하고, 대괄호와 뒤쪽의 구현 근거·실패 대안·체크리스트는 진행용이다.

## 역할과 화면

| 담당 | 역할 | 발표 중 유지할 화면 |
| --- | --- | --- |
| A · 발표자/제어실 | 발표, 시나리오 전환, 시간 관리 | `http://CNU.local:8080/demo` |
| B · 사용자 | Raspberry Pi 사용자 동작, AI 질문, 실제 통화 시작 | Pi 키오스크 `http://127.0.0.1:8080/?kiosk=1` |
| C · 보호자 | 알림 확인, 보호자 대시보드, 실제 통화 수락 | `https://CNU.local:8443/caregiver` |

보호자 화면은 발표 전에 PIN `3017`로 로그인한다. 세 화면은 같은 네트워크에 연결하고, 발표 중에는 모두 전면에 둔다.

## 실제 발표 대본과 조작 큐

### 00:00–00:35 · 문제와 해결 방향

**조작**

- [A는 사용자 화면의 큰 글씨 체크리스트와 안심 지수를 가리킨다.]
- [B와 C는 조작하지 않는다.]

**발표 멘트**

> 안녕하세요. 피우다는 초기 치매 환자와 경증 장애인이 일상을 스스로 수행하도록 돕고, 보호자는 꼭 필요한 순간에만 확인하도록 만든 Raspberry Pi 기반 자립생활지원 시스템입니다. 카메라로 생활을 촬영하는 대신 일정 수행 정보와 PIR, Wi-Fi CSI 생활 신호를 사용합니다. 화면의 점수는 의료 진단이 아니라 보호자가 확인 순서를 정하는 보조 정보입니다.

### 00:35–01:15 · 전체 데이터 흐름

**조작**

- [A는 사용자 화면, CSI 송신·수신 ESP32 두 대, 보호자 스마트폰을 차례로 가리킨다.]

**발표 멘트**

> 전체 흐름은 단순합니다. 한 ESP32가 초당 50개의 측정 패킷을 만들고, 다른 ESP32가 PIR과 Wi-Fi CSI 변화를 분석해 센서별 API 키와 함께 Raspberry Pi의 Flask REST API로 전송합니다. Pi는 반복 일정을 오늘의 체크리스트로 만들고, 일정과 센서 이벤트를 함께 점수화합니다. 결과와 알림은 SQLite에 저장되고 사용자 화면과 PIN 보호 보호자 화면이 2초 주기로 동기화됩니다. SQLite에는 외래 키와 WAL 모드를 적용해 여러 화면의 동시 조회와 기록을 처리했습니다.

### 01:15–02:05 · 반복 일정과 완료 기록

**조작**

1. [A가 제어실에서 `약 먹을 시간`을 실행한다.]
2. [약 2초 뒤 B가 강조된 `아침 약 복용`의 `완료했어요`를 누른다.]
3. [C는 보호자 화면의 일정 완료 상태가 바뀌는 것을 보여 준다.]

**발표 멘트**

> 보호자는 식사, 복약, 외출 같은 반복 일정을 등록할 수 있습니다. 서버는 요일을 비트마스크로 저장하고 오늘 날짜와 시간을 결합해 실제 수행 항목을 만듭니다. 같은 날짜의 일정이 중복 생성되지 않도록 일정 ID와 예정 시각을 유일키로 두었습니다. 지금 사용자가 완료 버튼을 누르면 상태와 완료 시각이 저장되고 점수를 즉시 다시 계산합니다. 큰 버튼, 짧은 안내, 완료 음성은 사용자가 혼자서도 다음 행동을 이해하도록 설계한 부분입니다.

### 02:05–03:05 · 비접촉 센서와 설명 가능한 점수

**조작**

1. [A가 제어실에서 `넘어짐 의심`을 실행한다.]
2. [B는 사용자 화면의 `50점 · 주의`를 보여 준다.]
3. [C는 보호자 화면에서 `Wi-Fi CSI 넘어짐 의심`, `신뢰도 91%`, `-50` 근거를 가리킨다.]

**발표 멘트**

> 송신 ESP32는 같은 2.4기가헤르츠 채널에서 초당 50개의 ESP-NOW 측정 패킷을 보냅니다. 수신 ESP32는 PIR 입력을 250밀리초마다 확인하고, Wi-Fi CSI의 I와 Q 값으로 신호 크기를 계산합니다. 초기 250개 패킷으로 기준선을 만든 뒤 변화율이 설정 임계값을 연속으로 넘으면 움직임 또는 넘어짐 의심 이벤트를 큐에 넣어 전송합니다. 서버의 실제 점수 엔진은 최근 30분 안에 들어온 신뢰도 0.65 이상의 CSI 넘어짐 신호를 50점 감점합니다. 그래서 지금 100점에서 50점이 되어 ‘주의’로 바뀌었고, 보호자는 결과뿐 아니라 신뢰도와 감점 이유까지 확인할 수 있습니다. 이번 발표에서는 실제 넘어짐을 만들지 않고 제어실이 같은 센서 조건을 재현했습니다.

### 03:05–04:10 · 사용자에게 먼저 묻고 필요한 때만 알림

**조작**

1. [03:05에 A가 `낮 시간 3시간 무활동`을 실행한다.]
2. [B는 확인 팝업이 뜨면 아무 버튼도 누르지 않는다.]
3. [C는 처음에는 새 보호자 알림이 없다는 것을 보여 준다.]
4. [약 03:37에 30초 카운트다운이 끝나면 C가 새 확인 알림을 보여 준다.]
5. [03:42까지 자동 전환되지 않으면 A가 `확인에 응답 없음`을 직접 실행하고 04:10에 다음 구간으로 넘어간다.]

**발표 멘트**

> 움직임이 없다는 이유만으로 보호자에게 바로 경보를 보내면 쉬고 있는 상황도 위험으로 오인할 수 있습니다. 피우다는 먼저 사용자 화면에 ‘지금 문제가 있나요?’라고 묻고 30초 동안 응답을 기다립니다. ‘괜찮아요’를 누르면 움직임을 다시 확인한 안심 장면으로 돌아가고 보호자 알림은 만들지 않습니다. 지금은 차이를 보여 드리기 위해 응답하지 않겠습니다. 브라우저가 활성 시각을 기준으로 매초 남은 시간을 계산하고, 30초가 지나면 로컬 wellness API에 timeout을 보냅니다. 이제서야 건강 점수가 30점으로 바뀌고 보호자에게 확인 요청이 생성됩니다. 이 선확인 흐름은 현재 발표 모드의 재현 가능한 장면으로 연결되어 있습니다.

### 04:10–04:55 · 보호자 대시보드와 인증

**조작**

1. [C가 건강 점수, 일정 진행, 감점 근거, 최근 센서 기록, 미확인 알림을 위에서 아래로 짚는다.]
2. [C가 새 알림의 `확인했습니다` 또는 `처리 확인`을 누른다.]

**발표 멘트**

> 보호자 화면은 오늘 일정, 건강 점수, 감점 근거, 센서 연결 상태, 최근 이벤트와 알림을 한 번에 조회합니다. 화면은 2초마다 갱신되고 새 위험 알림은 큰 팝업과 소리로 표시됩니다. 확인 버튼을 누르면 처리 시각이 기록됩니다. 보호자 PIN은 Werkzeug 해시로 저장하고, 로그인 토큰과 센서 API 키도 원문이 아니라 SHA-256 해시만 데이터베이스에 보관합니다. 대시보드의 변경·조회 API는 보호자 세션이나 bearer token을 요구합니다.

### 04:55–06:00 · 로컬 AI, 대화 기억, 안전 폴백

**조작**

1. [04:55에 B가 미리 복사한 `오늘 보리차를 마셨어요. 잘했죠?`를 붙여 넣고 보낸다.]
2. [응답을 기다리는 동안 A가 아래 멘트를 이어 간다.]
3. [응답 후 B가 `제가 아까 무엇을 마셨죠?`를 보내고, 답변의 `보리차`를 보여 준다.]
4. [05:15까지 첫 응답이 없으면 요청을 중복 전송하지 말고 두 번째 기억 질문을 생략한다. 설명은 계속하고 06:00에 통화 구간으로 넘어간다.]

**발표 멘트**

> 생활 도우미에는 현재 점수와 오늘 일정, 최근 대화를 함께 제공합니다. 일반 질문은 Raspberry Pi의 Ollama에서 한국어 특화 HyperCLOVA X SEED 1.5B Q4 모델로 처리하고, 최근 대화는 SQLite에 저장해 다음 응답에 반영합니다. 반면 ‘다음 할 일’, 특정 시간의 일정, 남은 일정, 119가 필요한 긴급 표현은 모델을 기다리지 않고 규칙 기반으로 즉시 답합니다. 모델이 지연되거나 실패해도 긴급 안전 문구 또는 다음 일정으로 폴백합니다. 답변은 길이와 마크다운을 정리한 뒤 Pi에서 한국어 음성으로 읽습니다. 두 번째 질문은 저장된 사용자 발화를 찾아 ‘보리차’라고 답하므로 기억을 추측하지 않습니다.

### 06:00–07:30 · 실제 양방향 음성 통화

> **필수 조작 순서:** A가 제어실 장면 실행 → B가 사용자 화면의 실제 버튼 클릭 → C가 수신 후 통화 수락. 순서를 바꾸지 않는다.

**조작**

1. [06:00에 A가 제어실에서 `보호자와 통화` 장면을 실행한다. 이 단계에서는 통화가 만들어지지 않는다.]
2. [사용자 화면에 버튼 안내가 반영될 때까지 약 2초 기다린다.]
3. [06:05까지 B가 사용자 화면 상단의 실제 `보호자와 통화` 버튼을 누른다. 이 gesture가 사용자 마이크를 연다.]
4. [C의 스마트폰에 수신 다이얼로그가 뜬 뒤 `통화 받기`를 누른다. 이 두 번째 gesture가 보호자 마이크를 연다.]
5. [연결되면 B: “피우다 통화 테스트입니다.” C: “네, 잘 들립니다.”]
6. [07:20까지 C가 `통화 종료`를 누르고, 양쪽 다이얼로그가 닫힌 것을 확인한다.]

**발표 멘트**

> 먼저 제어실의 통화 장면은 사용자에게 버튼을 누르라고 안내만 합니다. 마이크는 브라우저 보안 정책상 실제 사용자의 gesture가 필요하기 때문입니다. 지금 사용자 화면의 버튼을 누르면 사용자 마이크를 열고, 남아 있던 통화를 종료한 새 통화 ID와 WebRTC offer를 만듭니다. 서버가 offer 저장을 확인한 뒤에만 보호자 수신 화면을 띄웁니다. 보호자도 실제 ‘통화 받기’를 눌러 자신의 마이크를 연 뒤 answer와 ICE candidate를 교환합니다. 신호는 Pi의 REST API와 SQLite를 거쳐 이전 요청이 끝난 뒤 600밀리초 간격으로 확인하고, 음성은 WebRTC로 양방향 전달합니다. 외부 STUN이나 TURN이 없는 같은 Wi-Fi 전용 구조이며 스마트폰 마이크를 위해 8443번 로컬 HTTPS를 사용합니다. 종료하면 상태와 시각을 저장하고 양쪽 오디오 트랙을 정리합니다.

**통화 장면이 안내만 하는 이유**

- `piuda/demo.py`의 `caregiver_call` 장면은 안내 상태만 활성화하고 `calls` 레코드를 만들지 않는다.
- 실제 `calls` 레코드, 사용자 마이크 스트림, WebRTC offer는 사용자 버튼의 `callCaregiver()`에서 생성된다. 호출 시 `replace: true`를 보내 직전의 열린 통화와 신호를 재사용하지 않는다.
- 보호자 대시보드는 서버가 `offer_ready`를 반환한 통화만 수신 화면으로 보여 준다. 보호자의 `통화 받기` gesture가 보호자 마이크와 answer 생성을 시작한다.
- 제어실에서 미리 `ringing`만 만들면 offer가 없어 연결할 수 있으므로, **제어실 장면만 실행하고 기다리면 통화와 수신 화면 모두 시작되지 않는 것이 정상이다.**

### 07:30–08:00 · 회복과 결론

## 구현 범위를 정확히 말하기

- 제어실 장면은 발표의 재현성을 위해 데이터베이스에 정해진 일정·센서·점수 상태를 넣는다. 실제 센서에서 방금 발생한 물리 이벤트라고 표현하지 않는다.
- 일반 점수 엔진은 실제 일정과 센서 데이터를 평가하지만, 30초 사용자 선확인 다이얼로그와 `/wellness-check` 연결은 현재 데모 모드 장면에 구현되어 있다. 운영 환경 전체에 자동 배포된 기능이라고 과장하지 않는다.
- `센서 연결 끊김`은 일반 `RISK_RULES`의 25점 감점 항목이다. 마지막 신호가 없는 새 센서는 등록 시각부터, 신호를 받은 센서는 `last_seen_at`부터 30분 이상 지나면 적용된다.
- CSI는 임계값 기반의 **넘어짐 의심 보조 신호**다. 의료기기 판정이나 검증되지 않은 정확도 수치를 말하지 않는다.
- WebRTC는 `iceServers: []`인 같은 로컬 네트워크용 구현이다. 인터넷 어디서나 연결되는 통화라고 말하지 않는다. 통화 REST API도 사설 네트워크 요청만 허용하며, 보호자 대시보드 인증과는 별도의 경계다.
- 카메라는 사용하지 않지만 일정·센서·대화 기록은 Pi의 SQLite에 저장된다. “아무 데이터도 저장하지 않는다”라고 말하지 않는다.
- Ollama 모델 추론은 Pi에서 처리하지만 gTTS는 네트워크가 필요할 수 있고, 웹 SpeechRecognition도 브라우저 구현에 따라 외부 처리가 가능하다. “음성까지 완전 오프라인”이라고 말하지 않는다.
- PWA의 화면 셸은 캐시되지만 일정·센서 API 데이터에는 Pi 연결이 필요하다.
- SwiftUI 앱은 일정·대시보드·STT/TTS를 구현하지만, 현재 WebRTC 통화 데모는 웹/PWA 화면을 사용한다.
